# معايير قبول تقوية الباكند

## معنى 100% في هذا المشروع

تعني 100% أن كل فجوة معمارية مثبتة في مراجعة الباكند لها ضابط مركزي في الشفرة، وترحيل قاعدة بيانات عند الحاجة، واختبار يثبت عملها أو فشلها الآمن. لا تعني تصديقًا قانونيًا، ولا اختبار حمل حقيقيًا، ولا ضمان جاهزية خادم الإنتاج من دون تنفيذ قائمة تشغيله.

## معايير القبول

| المحور | شرط القبول |
|---|---|
| عزل الشركات | يوجد QuerySet/Manager مركزي مقيد بالشركة، ولا تعتمد endpoints الجديدة على فلترة متفرقة فقط؛ توجد اختبارات محاولة قراءة وكتابة عبر شركتين. |
| العضويات | علاقة المستخدم بالشركة قابلة للتمديد عبر عضوية صريحة، مع بقاء العلاقة القديمة متوافقة أثناء الترحيل. |
| حالة الرحلة | يوجد مصدر واحد قابل للحساب لحالة رحلة الشركة، ولا تظهر حالة `certified` كإقرار رسمي. |
| الاستحقاقات | لا توجد ميزة مدفوعة قابلة للوصول من دون gate موحد، وتتحقق الحدود داخل معاملات قاعدة البيانات. |
| الدفع | تسجل أحداث مزود الدفع بصورة append-only ومتفردة حسب المزود ومعرف الحدث، وإعادة تسليم الحدث لا تغير الحالة مرتين. |
| المهام | لكل مهمة تشغيلية قفل موزع، وحالة تشغيل، وتقسيم قابل لإعادة المحاولة لكل شركة. |
| التدقيق | أحداث التدقيق append-only، وتُرفض محاولة التعديل أو الحذف عبر مسار التطبيق. |
| النسخ الاحتياطي | توجد أوامر نسخ/تحقق/استرجاع جافة موثقة وفحوص تشغيل قبل النشر. |
| المراقبة | تتوفر endpoint أو إدارة لإظهار صحة قاعدة البيانات وRedis والعامل وBeat وأعمار المهام الأساسية. |

## نطاق متعمد

تُنفذ هذه المعايير داخل التطبيق والحاويات. تتطلب مفاتيح التخزين والكائنات وخطة النسخ الفعلية في الإنتاج استكمال متغيرات البيئة وتنفيذ تشغيل منفصل على الخادم.
